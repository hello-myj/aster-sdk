# OpenOMF 实体设备适配：源码确认记录

## 结论

连续混音、实时声像参数与独立BGM生命周期可以在固件音频线程中实现；它们需要固件、SDK契约和模拟器同步，单改SDK头文件不能让已经刷入的固件获得能力。本轮只落地并构建验证了工具修复，音频运行时扩展尚未实现或烧录。

完整OpenOMF当前版本不能直接部署到8MiB PSRAM的微雪板。并非AOT文件大于内部IRAM就必然失败：当前固件模块platform/zephyr已经支持PSRAM可执行映射。主要障碍是总PSRAM预算与加载峰值，帧率也必须实机测量。

## 内存证据

当前APP固定12,582,912B线性内存，内部8,388,608B有界C堆；Guest导出的__heap_base为9,072,496B，扣除该C堆的其余静态区与栈为683,888B。已观察C堆峰值3,924,080B，不包含堆块头、碎片或未遍历的最终Boss/结局。

当前AOT文件1,802,820B，TEXT章节1,423,748B。固件aster_runtime.c的ctx_load保留ctx->img，WAMR aot_loader.c的create_sections又为TEXT申请可执行PSRAM并复制，故文件和可执行TEXT至少合计3,226,568B，尚不含PLT/运行时元数据。

即使把C堆静态预留缩到恰好等于已观察峰值，只加C堆峰值、其余静态区/栈、524,288B Host管理堆和上述AOT两份存储，就已8,358,824B，约7.97MiB。微雪配置的外部堆上限为7,864,320B，还需要固件、Host画面、音频缓存与解码器等，因此不能靠直接把initial_memory改小解决。

## 后续实际实施顺序

1. 优先消除AOT镜像中TEXT与可执行TEXT的重复存储：研究按章节加载/所有权管理或闪存执行缓存；严格保留重定位、I/D总线镜像与缓存刷新，不直接释放仍被模块引用的ctx->img。
2. APP按真实场景峰值收缩有界池和线性内存；评估软件中间帧缓冲压缩，保持原版调色板/阴影语义。必须遍历不同机器人、场地、锦标赛和结局，不能只以当前一组对战为最高值。
3. 音频新增能力保持4.1结构与旧行为不变，使用新的正式契约版本；在固件音效DSP增加独立左右增益平滑更新，不重置相位。BGM切换/循环由音频工作线程推进，和音效缓存/播放生命周期分离，不能靠FRAME反复重播或在新接口里调用全局stop。
4. 同步SDK公开手册/导入表和模拟器，再由OpenOMF适配层使用新增能力。验证微雪真实SD、音乐与三路效果声的复合负载；模拟器不能替代实机验收。

本轮未改动或烧录固件；独立克隆的aster-firmware和aster-sim检出用于核对现状，保持源码干净。安装版SDK和APPS保持原工作位置。
